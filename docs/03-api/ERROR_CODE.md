# 错误码规范

> 所有 API 错误响应必须使用统一结构，便于前端展示和测试断言。

---

## 1. 错误响应格式

```json
{
  "code": 10001,
  "message": "Project Not Found",
  "data": null
}
```

字段说明：

| 字段 | 类型 | 说明 |
|------|------|------|
| `code` | int | 平台业务错误码 |
| `message` | string | 可读错误信息 |
| `data` | object/null | 错误附加信息，默认 null |

---

## 2. HTTP 状态码

| HTTP | 说明 |
|------|------|
| 200 | 成功 |
| 201 | 创建成功 |
| 204 | 删除成功，无响应体 |
| 400 | 请求语义错误 |
| 401 | 未认证或 Token 无效 |
| 403 | 无权限 |
| 404 | 资源不存在 |
| 409 | 资源冲突 |
| 422 | 参数校验失败 |
| 500 | 服务端异常 |

---

## 3. 通用错误码

| code | HTTP | 说明 |
|------|------|------|
| 0 | 2xx | 成功 |
| 10000 | 400 | 通用请求错误 |
| 11001 | 401 | 未登录 |
| 11002 | 401 | Token 无效或过期 |
| 11003 | 403 | 权限不足 |
| 12001 | 409 | 资源已存在 |
| 13001 | 422 | 参数校验失败 |
| 99999 | 500 | 系统内部错误 |

---

## 4. 认证与用户错误码

| HTTP | 业务 code |  说明 |
|------|------|------|
| 401 | `INVALID_CREDENTIALS` | 用户名或密码错误（20001，登录接口统一返回同一业务码以防枚举） |
| 403 | `ACCOUNT_DISABLED` | 用户已禁用（20002） |
| 409 | `USERNAME_TAKEN` | 用户名已存在（20003） |
| 409 | `EMAIL_TAKEN` | 邮箱已存在（20004） |
| 404 | `USER_NOT_FOUND` | 用户不存在（20005） |
| 400 | `INCORRECT_OLD_PASSWORD` | 旧密码错误（20006） |
| 401 | `TOKEN_INVALID` | Token 无效/过期/已吊销/版本过期（11002） |
| 403 | `FORBIDDEN` | 操作被拒绝（含“需超级管理员鉴权”） |
| 429 | `TOO_MANY_REQUESTS` | 限流/登录锁定 |
| 404 | `ROLE_NOT_FOUND` | 角色不存在（21001） |
| 409 | `ROLE_EXISTS` | 角色已存在（21002） |
| 400 | `ROLE_SYSTEM_IMMUTABLE` | 系统角色不可删除（21003） |

---

## 6. 使用原则

1. HTTP 状态码表达通用语义。
2. `code` 表达平台业务原因。
3. `message` 应清晰但不泄露敏感信息。
4. 登录失败不要暴露用户是否存在。
5. 执行异常应保存到 `api_test_results.error_message`，但日志需脱敏。
